# Read the Runes — Product decisions and parity matrix

Base audited: `4c87a1f573c59fd609cada90115436b3d8aca8c5` (`main`). This is the approved Stage 2 product contract and Stage 1 parity record for the first release. It records requirements; it is not evidence that implementation or testing has passed. Update verification evidence in the delivery PR.

## Binding product decisions

- **Core loop:** identify one hidden card artwork among four fixed choices for the MVP (the supported design range is four to six). Runes are progressively revealed clues derived dynamically from verified card-catalog metadata. This is not a secret-symbol sequence game and has no Exact/Misplaced feedback.
- **One answer:** the first clue is revealed automatically and counts toward clues used. Further clues are revealed one at a time and all revealed clues remain reviewable. Artwork choices and their order remain fixed. Selection can change until the player explicitly confirms one answer. A correct answer wins immediately; an incorrect answer loses immediately. Revealing the final available clue does not end the round; one answer remains possible. No gameplay actions are accepted after resolution.
- **Artwork identity:** distinguish logical card, pitch variant, printing, and artwork identity. The answer is the specific displayed artwork/printing. Collapse or exclude any candidates with identical or ambiguous artwork; do not allow variants of the same image to appear as separate answers. During active play expose only original artwork crops and neutral option labels. Reveal card identity and full card after resolution.
- **Clue integrity:** facts must be available, accurate, unambiguous, and scoped to the exact displayed art/printing. Candidate categories include type, subtype, class, talent, rarity, cost, pitch, defense, artist, and verified release facts. Omit missing/conflicting facts; never fabricate data, reveal the complete card name, duplicate or contradict clues, or place hidden clues in client-accessible state. Generate varied, broadly-to-specifically ordered clue sequences using the current candidate set; ensure the complete valid sequence leaves exactly one correct artwork. Reselect/fail safely if a valid round cannot be generated.
- **Timing and ranking:** begin timing only after all answer artwork is ready for interaction; stop at answer confirmation. Asset loading and result animation are excluded. Reviewing clues or help does not pause time. Only authenticated wins enter the leaderboard and establish personal bests. Sort lexicographically by fewest clues, then elapsed completion time; equal clue count and time share rank. Any future configuration that changes comparability must be separated in rankings.
- **Actors, persistence, and stats:** guests may play but are excluded from authenticated leaderboard and personal bests. Authenticated wins/losses contribute to Runes-owned statistics; best records use wins only. Keep Runes data separate from Guess `UserStat`/`UserCardStat` and other game aggregates. API owns transitions, actor/session checks, clue limits, answer validation, timing, and result eligibility. Persist/recover active state according to platform conventions and make result persistence idempotent. Tutorial never contributes to stats, records, or rankings.
- **Tutorial:** deterministic practice uses the real **Read the Runes** ARC109 First, non-foil artwork crop, plus three real, distinct distractor artworks. It uses the same clue/answer evaluator and controls, permits early confirmation with the same immediate win/loss rules, and reveals the full correct card after resolution. Replay resets the fixture.
- **MVP boundary:** solo play only. Do not expose unimplemented co-op, competitive, challenge, or sharing actions. This is an approved exception: those modes require equivalent seeded target, options, clue sequence, lifecycle, and synchronization. Future support should use existing shared room/challenge/WebSocket infrastructure rather than a parallel social system.

## Acceptance gate for implementation and PR review

1. **Generation:** tests prove eligible/ineligible target behavior, exact-art metadata scope, distinct crops, no duplicate or ambiguous candidates, clue variety/order/nonduplication, max-sequence uniqueness, deterministic tutorial, and safe no-pool behavior.
2. **Lifecycle:** first clue is automatic and counted; reveal limits enforced; history and selection retained; fixed options; one confirm; correct win/incorrect immediate loss; final clue still allows a final answer; terminal actions rejected; ready-to-submit timer boundaries are correct.
3. **Authority and persistence:** owner/actor/config/state validated; invalid bearer fails closed; guest remains playable and excluded from authenticated standings; retry/duplicate/concurrent completion is idempotent; stats and records update exactly once and only wins establish best/rank.
4. **Privacy/artwork:** review API responses, browser DOM/accessibility tree, alt text, links/URLs, logs and network payloads during play; only cropped unmodified card artwork is visible. Full card/identity appears after result. Document realistic image-identification residual risk.
5. **Parity and UX:** hub/header, setup, help, FAQ, leaderboard, stats, results, loading/empty/error and replay actions follow platform patterns; no unsupported social mode is shown; matrix rows link to implementation and actual verification evidence.
6. **Tutorial:** target is Read the Runes ARC109 artwork, not another card; real distractors and catalog facts; same game evaluator and answer flow; early correct/incorrect behavior; replay reset; full card reveal; no stats/ranking mutation.
7. **Accessibility/playtest:** desktop and mobile sessions include a win, an incorrect-answer loss, final-clue case, keyboard tutorial, 200% zoom, reduced motion and viewport sizes above. Perform at least one evidence-based refinement and record observed behavior; do not report unperformed sessions.
8. **Quality/delivery:** automated tests, type checks, lint and builds actually run; applicable regressions checked; independent review of final PR diff/CI has no unresolved critical/high finding; exactly one PR targets `main` and remains unmerged/undeployed.

## Decisions still requiring implementation evidence (not product approval)

- Whether the chosen active-session storage survives API process restart in the same way as other games. The implementation must either provide recovery or state the concrete limit in PR known limitations.
- Whether all candidate data in the installed catalog supports robust art fingerprinting. If the image service exposes only identifiers rather than bytes, validate the mapping and document any remaining reverse-image lookup risk.
- Actual playtest findings, check results, independent reviews, CI and deployment requirements. These must be filled with observed evidence in the PR; this document alone does not satisfy them.
